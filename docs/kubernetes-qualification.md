# Kubernetes Helm qualification

The Kubernetes CI drill builds the application images from the checked-out release commit, loads them into a uniquely named disposable kind cluster, then installs the actual ZeroGraph chart with production settings and private generated Secret values. PostgreSQL, Redis and Memgraph are synthetic test fixtures with PVCs inside that cluster. No external Kubernetes context, public ingress, cloud account or operator database is used.

Run `python deploy/kubernetes.py --ci-disposable` only on an explicitly disposable CI runner (`CI=true`) with Docker, kind, kubectl, Helm and PyYAML installed. The runner creates a private temporary kubeconfig, verifies the exact context, loopback API endpoint and Docker node ownership label before Kubernetes/Helm access, and removes only its owned cluster. Existing clusters are never reused. Failures expose bounded operation labels; artifacts exclude kubeconfigs, Secret values, DSNs, manifests and pod logs. Generated credentials and private temporary files are removed when the process exits normally; a forcibly killed disposable runner requires runner-level destruction.

Assertions cover fresh SQL/graph migrations and migration hook success, actual Deployment readiness and Service endpoints, hardened application containers, startup/readiness/liveness probes, protected API and metrics, disabled demo sign-in, singleton scheduler, ConfigMap-triggered pod replacement during upgrade, and a coherent synthetic SQL revision pointer plus graph nodes/edges after application and PVC-backed store pod restarts. Uninstall and owned namespace/cluster deletion are checked. The sanitized JSON artifact records the source commit, image tags/runtime image IDs, Kubernetes version, hook execution and persistence proof.

This tests one-node ephemeral fixture persistence across pod restarts. It does not qualify managed storage recovery, node loss, scale, customer networking, ingress TLS, external identity sign-in or production capacity. The unreachable HTTPS issuer is deliberately a configuration fixture; authentication is never bypassed and no sign-in claim is made. The upgrade re-executes the current migration head with a configuration change; it does not qualify arbitrary historical database upgrades or mixed-version workers. Drain old workers before the documented incompatible ingestion migration.

Tool versions are fixed in CI: [kind v0.33.0 and its Kubernetes v1.36.4 node digest](https://github.com/kubernetes-sigs/kind/releases/tag/v0.33.0), kubectl v1.36.4, Helm v3.17.3. Downloaded kind/kubectl binaries are checksum-verified. The chart uses [Helm migration hooks](https://helm.sh/docs/topics/charts_hooks/); successful hook Jobs are deleted, and the drill inspects private Helm release state to verify each hook run. Hook ConfigMaps are explicitly cleaned because hook resources are not ordinary release-managed objects.

Before deployment, qualify the exact release on the authorized target Kubernetes version, registry, storage class, protected ingress/TLS and identity provider, including coordinated backup/restore and upgrade procedures. This CI artifact is installation evidence, not authorization to deploy or a production recovery guarantee.
